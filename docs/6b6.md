# Phase 6B.6 — Chaitanyam AI Conversation Persistence & History

**Status: Complete and verified.**

This document is the source-of-truth completion record for Phase 6B.6 of the Happy Soul Krishna AI system.

---

## 1. Purpose & Scope

Phase 6B.6 provides **conversation persistence and UI history restoration** for authenticated Chaitanyam AI users. It enables users to:

- View their recent conversation list inside the Chaitanyam drawer
- Select and reopen a previous conversation to continue it
- Have unsent draft text cleared automatically when switching conversations
- Send follow-up messages into an existing (restored) conversation

> **Important limitation:** Phase 6B.6 provides conversation persistence and UI history restoration. It does **not** yet provide an AI context window or send previous conversation messages to Gemini. Gemini still receives only the new user message — prior conversation content is displayed in the UI but not injected into the AI prompt.

**Conversation history is limited to the most recent 20 conversations and up to 100 messages per selected conversation in this phase.**

## 4. API Endpoints

### 4.1 `GET /api/krishna/conversations`

Lists the authenticated user's recent conversations.

**Authentication:** Supabase SSR (`supabase.auth.getUser()`). Returns `401` if unauthenticated.

**Ownership:** Explicit `.eq("user_id", user.id)` + RLS (defense-in-depth).

**Response:**
```json
{
  "conversations": [
    {
      "id": "uuid",
      "title": "How can I deal with overthinking?",
      "createdAt": "...",
      "updatedAt": "..."
    }
  ]
}
```

**Limit:** 20 conversations, ordered `updated_at DESC`.

**Not returned:** `user_id`, `retrieval_meta`, `is_flagged`, internal DB metadata.

---

### 4.2 `GET /api/krishna/conversations/[conversationId]`

Returns a specific conversation's header and messages.

**Authentication:** Supabase SSR. Returns `401` if unauthenticated.

**Ownership:** Fetches conversation with `eq("id", conversationId)`. Verifies `conversation.user_id === user.id`. Returns `404 CONVERSATION_NOT_FOUND` for any mismatch — does NOT distinguish "not found" from "belongs to another user" to prevent enumeration.

**UUID validation:** Input is validated against a UUID regex before hitting the DB.

**Response:**
```json
{
  "conversation": {
    "id": "...",
    "title": "..."
  },
  "messages": [
    {
      "id": "...",
      "role": "user",
      "content": "...",
      "createdAt": "..."
    },
    {
      "id": "...",
      "role": "assistant",
      "content": "...",
      "citedVerseIds": ["uuid"],
      "citations": [
        { "chapter": 2, "verse": 47 }
      ],
      "createdAt": "..."
    }
  ]
}
```

**Limits:**
- 100 messages max, ordered `created_at ASC` (chronological)
- If a conversation has > 100 messages, the **oldest 100** are returned so the conversation reads chronologically from the beginning. The newest messages beyond 100 are silently truncated. This is a known limitation (see Section 12).

**Citation resolution:** All `cited_verse_ids` across all assistant messages in the conversation are collected in a **single** `gita_verses` lookup (one DB round-trip). The chapter/verse number is mapped back per message. This avoids N+1 queries.

**Not returned:** `user_id`, `retrieval_meta`, `is_flagged`, raw DB error details.

## 5. API Client Helper (`components/krishna/api.js`)

Two new exports added (Phase 6B.5's `sendChaitanyamMessage` unchanged):

### `fetchConversations({ signal })`
- Calls `GET /api/krishna/conversations`
- 10-second timeout
- Returns `{ ok, conversations }` or `{ ok: false, error, status }`

### `fetchConversationMessages(conversationId, { signal })`
- Calls `GET /api/krishna/conversations/[conversationId]`
- 10-second timeout
- Returns `{ ok, conversation, messages }` or `{ ok: false, error, status }`

Both use the same abort-signal + timeout pattern as `sendChaitanyamMessage`. Error messages are safe and user-facing (no raw DB errors).

## 6. Provider Changes (`components/krishna/ChaitanyamProvider.jsx`)

### New State
| State | Type | Purpose |
|---|---|---|
| `showHistory` | `boolean` | Controls which view the drawer renders |
| `conversationsList` | `array` | Cached list of recent conversations |
| `loadingHistory` | `boolean` | True while fetching conversation list |
| `historyError` | `string\|null` | Error message for history list failures |
| `loadingConversationId` | `string\|null` | ID of the conversation currently being loaded |

### New Methods (exposed via `useChaitanyam()`)
| Method | Purpose |
|---|---|
| `toggleHistory()` | Switches between ACTIVE CHAT and HISTORY views |
| `loadConversationsList()` | Fetches conversation list (deduplicated per session) |
| `loadConversation(id)` | Loads messages for a specific conversation, replaces current state |
| `refreshConversationsList()` | Forces a fresh fetch (ignores the session cache) |

### Existing Methods (unchanged)
`openChat`, `closeChat`, `startNewConversation`, `sendMessage`, `retry`

### History Loading Strategy
History is fetched **on demand** when the drawer opens, **once per drawer open session** (tracked by `historyFetchedRef`). Subsequent toggles to the history view reuse the cached list. Sending a new message invalidates `historyFetchedRef` so the next open refreshes the list (new conversation would appear).

The drawer remains **closed** after page refresh — history is never pre-fetched while the drawer is hidden.

## 8. Refresh Restoration Behavior

After a browser refresh:
1. Dashboard loads (server component).
2. `ChaitanyamProvider` mounts — all state initializes to empty.
3. Drawer remains **closed**.
4. User opens Chaitanyam (via floating button or QuickActions card).
5. `loadConversationsList()` fires automatically (fetches recent 20).
6. User switches to History view → list is shown.
7. User selects a conversation → messages are fetched and displayed.
8. Drawer returns to ACTIVE CHAT view with loaded messages.
9. User can send follow-up messages using the restored `conversationId`.

---

## 9. Conversation Reopening

When a conversation is selected from history:
1. Any in-progress message send is aborted (`abortControllerRef.abort()`).
2. `requestGenRef` is incremented to invalidate stale in-flight requests.
3. `fetchConversationMessages()` is called with a fresh `AbortController`.
4. On success: `messages` is **replaced** (not appended) with loaded messages.
5. `conversationId` is set to the loaded conversation's ID.
6. Any unsent draft in the input textarea is cleared (`ChaitanyamInput` watches `conversationId`).
7. `showHistory` is set to `false` — drawer returns to ACTIVE CHAT view.
8. Future `sendMessage()` calls pass this `conversationId` to `POST /api/krishna`, appending to the existing conversation.

---

## 10. New Conversation Behavior (unchanged from 6B.5)

`startNewConversation()`:
- Aborts active request
- Increments `requestGenRef`
- Clears messages, conversationId, error, lastFailedText
- Sets `showHistory` to false
- Does **NOT** delete the previous DB conversation — it remains in history

## 11. Concurrency Protection

The existing `requestGenRef` / `AbortController` mechanism from Phase 6B.5 is reused for conversation loading:

```
User selects conversation A → currentGenA = requestGenRef.current (e.g. 5)
User quickly selects conversation B → requestGenRef.current becomes 6
Response A arrives → currentGenA (5) ≠ requestGenRef.current (6) → DISCARDED
Response B arrives → currentGenB (6) = requestGenRef.current (6) → ACCEPTED
```

A second `AbortController` (`historyAbortRef`) is used for history list GET requests specifically, so history fetches can be cancelled independently of message sends.

## 12. Authentication & Security

| Check | Implementation |
|---|---|
| Authentication required | `supabase.auth.getUser()` — 401 if missing |
| Ownership: conversation list | Explicit `.eq("user_id", user.id)` + RLS |
| Ownership: single conversation | Explicit `conversation.user_id === user.id` check after fetch |
| Cross-user 404 | No distinction between "not found" and "belongs to another user" |
| RLS | Enabled on `conversations` and `messages` (Phase 6B.1, unchanged) |
| No URL query params | `conversationId` passed as path param only, never in query string |
| No localStorage persistence | Messages stored in-memory only; history fetched from server |
| No secrets exposed | `user_id`, `retrieval_meta`, `is_flagged` stripped from all responses |
| User reset | `SIGNED_OUT` and `userId` change both call `resetAllState()` which clears all history state |

## 14. Performance

- Conversation list: bounded to **20** items, fetched once per drawer open session
- Message fetch: bounded to **100** messages per conversation
- Citation lookup: one batch `gita_verses` query for all verses in a conversation (no N+1)

- No automatic message pre-fetching for all conversations

## 19. Known Limitations

1. **Message truncation at 100:** Conversations with > 100 messages return the oldest 100 first. The newest messages beyond 100 are not shown.
2. **No AI context window:** Previous messages are shown in the UI but are not sent to Gemini. The AI responds only to the new message.
3. **History list not real-time:** The conversation list is fetched once per drawer open session. Conversations started in another browser tab are not reflected until the drawer is closed and reopened.
4. **No pagination:** The 20-conversation history limit has no "load more" option in this phase.
5. **Citation restoration uses chapter/verse only:** `GitaCitationBadge` displays `Bhagavad Gita X.Y` — full verse detail cards (Sanskrit text, translation, commentary) are deferred to a future phase.
